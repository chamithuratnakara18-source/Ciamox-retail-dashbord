# RetailFlow dashboard — secured Firebase package

This package keeps the existing dashboard UI and adds sign-in, role checks, a server-side write API, deny-by-default Firestore rules, and audit records. It is the **main dashboard only**. The phone scanner is a separate website. The default Firebase project is `ciamox-retail`.

## Security setup before deployment

1. In Firebase Authentication, enable Email/Password and create staff accounts yourself. This dashboard has no public sign-up flow.
2. Extract this ZIP into the Vercel project root and keep the `api` and `scripts` folders. Use Node.js 22 for the Vercel project; Firebase Admin SDK 14 requires Node.js 22 or later. Vercel deploys the `api/[...path].js` serverless route with the static dashboard.
3. In Vercel Project Settings → Environment Variables, add `FIREBASE_PROJECT_ID=ciamox-retail` and `FIREBASE_SERVICE_ACCOUNT_JSON` containing a dedicated runtime service-account JSON value. Store it only as a Vercel secret; never put it in `firebase-config.js`, source control, the ZIP, or a browser bundle. Give the runtime account only the Cloud Firestore read/write access needed by this API and Firebase Authentication Viewer access for token-revocation checks. Admin SDK requests bypass Firestore Rules, so API role checks are mandatory. If using the separate phone-scanner site, add `RETAILFLOW_SCANNER_ORIGIN` with its exact HTTPS origin (no wildcard) so its authenticated API calls pass CORS checks.
4. In Firestore → Rules, publish the included `firestore.rules`. They allow reads only to signed-in accounts with an approved `retailRole`; all browser writes and unknown collections are denied. The API performs writes after validating the Firebase ID token and role.
5. Create a separate, short-lived bootstrap credential with permission to manage Firebase Authentication users. In a trusted local shell, set `FIREBASE_ADMIN_BOOTSTRAP_JSON` to that credential and `FIREBASE_PROJECT_ID=ciamox-retail`, then run `npm run set-role -- staff@example.com manager`. Repeat with `owner`, `admin`, `manager`, or `cashier` as appropriate. Do not store this bootstrap credential in Vercel. The staff member must sign in again after a role is assigned or changed.
6. Deploy only after the phone scanner has also been updated to sign in and send reads/writes to this API. The scanner is a separate app and is not in this ZIP; publishing the included rules before that app is migrated will block its old direct Firestore reads and writes.

Role permissions are enforced by the server and Firestore Rules: cashiers can use POS only and can read only the current POS cart; owner/admin/manager can read dashboard, inventory, sales, receipts, and Finance; owner/admin/manager can receive stock, edit categories and prices, and manage Finance; only owner/admin can delete inventory. The POS catalog API removes purchase costs and supplier/date fields for cashiers. The browser login also hides non-POS screens for cashiers, but the backend and Firestore Rules are the actual access controls.

The Firebase web config in `firebase-config.js` is public by design. Do not put any service-account key or other secret there. Restrict its API key to the deployed website referrers and only the Firebase APIs the app needs; include the scanner origin when you migrate that app. This single Firebase project currently models one store and does not provide tenant separation between multiple stores.

## Connect Firebase

Use the existing default **Standard** Firestore database and Firebase project. Firebase Hosting is optional; this package can stay on Vercel. Extract the ZIP into the Vercel project root and retain its folders (`api`, `scripts`) and root files. The Product categories cards remain about 320px wide, with the product name, supplier, manufacture date, and expiry date below each photo.

## Check the connection

After configuring Firebase Authentication, the role claim, the API secret, and Firestore Rules, sign in with an approved staff account. The status should say `FIREBASE CONNECTED`. Inventory, POS, dashboard, Finance, and analytics continue using the same live Firestore records. Verify that each staff role can only perform its documented actions before inviting staff to use the system.

## Dashboard overview

Choose **Day**, **Month**, or **Year** and a date at the top. Revenue and orders count completed sales for that period. Their change compares with the preceding day, month, or year; for a current, unfinished month or year the comparison covers the same elapsed portion of the prior period. When the previous period is zero, the badge says **New activity** instead of showing an infinite percentage. The orange revenue and green gross profit chart groups a month by seven-day spans and a year by month; day view shows one daily total because sales do not have reliable hourly data. Missing purchase cost leaves gross profit unavailable rather than zero.

**Stock Alerts** and **Products** describe current inventory regardless of the selected sales period. Out of stock is Critical; 1–5 units is Low. Filter alerts with All, Critical, or Low. **Best Selling Item Share** has its own period and date controls. Its 3D ring sizes slices by units sold, including products later removed from inventory. Every sold product has its own color, without grouping later products into Other. The Bar chart includes every product sold in either the selected or previous matching period. A product keeps the same color in both views; the light shade of that color represents its previous-period bar. Scroll horizontally when many products are shown. The ring's depth is visual only; all numbers are derived from recorded sale items. If there are no matching sales, it shows an empty state.

## POS Sale

The left side shows searchable product photo cards and an **In stock** filter. Tap a priced, stocked product to add it to the current order. Phone scanning will use the same order after the separate scanner is migrated to sign in and call this API; its previous direct Firestore integration is blocked by the included Rules. The right side shows quantities, prices, subtotal, and total. Change quantities, remove an item, or clear the order there. Choose Cash, Card, or QR and click **Complete sale** after collecting payment. Card and QR choices record the method only; the app does not charge the customer. Checkout reads the current shared order and stock in a Firestore transaction, writes one sale, reduces stock, then clears the order; a second checkout of the cleared order cannot create another sale. The API supports remote scan updates, but the scanner source is not included in this ZIP and must be migrated before publishing the new Firestore Rules.

Set selling prices in **Finance** before checkout. A product without a price or purchase cost cannot be checked out. The active order is shared store-wide. Use **Clear order** on the dashboard to empty it.

## Finance

The **Inventory pricing** table shows each product's current weighted average purchase cost from Inbound, editable selling price, and gross profit per unit (`selling price - purchase cost`). The gross profit preview changes while you type. Click **Save price** to use that price for future sales. Past sales keep their recorded prices and costs. The POS uses the current saved price at checkout.

Click the arrow on **Monthly costs** to expand or collapse the form. Enter water, electricity, gas, sewage, total employee salaries, and the full monthly mortgage payment **including interest**. Fields that do not apply can be left blank. Enter at least one monthly cost before saving; until then, gross profit remains visible and net profit says **Unavailable**.

The **Monthly cash commitments** total tells you how much to keep for these bills. There is no per-item allocation because the app no longer asks how many units you expect to sell. Product rows still show instant gross profit per unit as you enter a selling price.

The four Finance summary rings show **Fixed costs / month** (the saved utilities, salaries, and full mortgage payment), **Product purchase cost / month** (positive Inbound receipt quantity × purchase price), **Gross profit / month** (sales less their recorded product cost), and **Net profit / month** (cash basis). Each badge shows the signed amount changed against the **previous calendar month**. Product purchase cost is money spent receiving stock, not the cost of goods sold in the gross profit calculation, so do not subtract it a second time. Stock deletions do not erase purchase history. The ring is decorative; its arc does not represent a percentage.

Saving Monthly costs also saves a plan snapshot for the current month. After installing this update, save the existing monthly amounts once to record this month's baseline. Previous fixed costs and net profit changes appear only after a plan was saved in that previous month. Existing plans saved before this update have no historical snapshots, so their previous month comparison reads **Previous month unavailable**. An incomplete purchase cost record makes that month's purchasing total unavailable rather than displaying a misleading zero.

The monthly net figure calculates **gross profit − utilities − salaries − the full mortgage payment − one-time expenses**. It works with a combined mortgage payment and can be negative when costs exceed gross profit. This is **cash after bills**, which differs from formal accounting net income because mortgage principal is a cash payment rather than a profit expense. Gross profit remains visible and net profit says **Unavailable** only when no monthly plan is saved or this month's sale cost data is missing. Do not record the same recurring bill in **One-time expense** or it will count twice. Editing the monthly plan recalculates the current month and saves a historical snapshot for that month.

In **Inventory**, each row has an **Add category** action before **Delete**. Choose to create a category or assign the product to an existing one. The category is stored on the existing product document, and the Product categories tab derives its list from those products; no extra Firestore collection or rule is required. The tab has category filters, product search, and cards showing stock, supplier, manufacture date, and expiry date. The secured inbound API stores optional manufacture and expiry dates on the product record. Managers read inventory from the `products` collection; cashiers receive a limited POS product view from the API. **Inventory analytics** follows the dashboard's pale background, heading, rounded white cards, navy text, green accents, and chart-title styling, while keeping the four analysis panels and interactions from the supplied `inventory-dashboard.html`. It uses live product, receipt, and sale records: stock-value category treemap with product drilldown, ABC analysis, expiry chart and table, and running-out chart and table. Category names, products, values, expiry dates, and sales rates are read from Firebase; sample categories and records are not used. The stockout window can be changed to 7, 30, or 90 days. Stock-value charts and ABC classification require saved purchase costs. Products without expiry dates are omitted from expiry risk, and products without recent sales have no stockout estimate. Each row also has a **Delete** button. Confirming removes that product and its remaining stock, and records a negative stock adjustment in the existing `receipts` collection. Past sales and revenue are retained in history. If the quantity or name changed after the row loaded, the operation stops and asks you to refresh.

The Dashboard has no Financial snapshot or Performance trend panel. The Revenue Chart still provides day, month, and year views of completed sales. Monthly financial totals and the **One-time expense** action are in Finance.

Data previously stored in TiDB is not moved automatically. This prototype reads `products`, `receipts`, `sales`, and `expenses` collections in the new Firestore database.
